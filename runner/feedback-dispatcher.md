# Event Feedback Dispatcher (Phase 4.3)

Turns new training events detected by the event poller (`runner/event-poller.md`) into short hybrid coaching feedback, generated by Claude under `workflows/event-feedback.md` and delivered through Telegram.

**Status: built and tested in simulation only.** Not deployed: the production store is still schema v1, the systemd units are templates and are not installed, and `FEEDBACK_DISPATCH_ENABLED` is unset. No live Claude call or Telegram message has been made by this component.

---

## Architecture

```
poller timer (:02/:17/:32/:47)          dispatcher timer (:07/:22/:37/:52)
event_poller.py --once                  feedback_dispatcher.py --once
  detect-only, no Claude/Telegram         reads config.env (Claude + Telegram)
  writes v1 tables                        writes v2 tables only
          \                              /
           runtime/events.sqlite3 (schema v2)
```

The poller stays detect-only: it imports none of the dispatcher, Claude or Telegram modules, its unit keeps `InaccessiblePaths` on `~/.claude` and `runner/config.env`, and nothing about its schedule changed. The two programs share only the SQLite file; each uses its own lock (`runtime/locks/event-poller.lock`, `runtime/locks/feedback-dispatcher.lock`) and `BEGIN IMMEDIATE` transactions.

| File | Role |
|---|---|
| `runner/feedback_dispatcher.py` | Orchestration, outbox processing, simulation, migration commands, CLI. |
| `runner/feedback_policy.py` | Pure rules: eligibility, staleness, quiet hours (DST-aware), grouping, level. |
| `runner/feedback_claude.py` | Prompt, output contract and validation, auth preflight, call classification. |
| `runner/feedback_store.py` | Schema v2 migration and the dispatcher's store access. |
| `workflows/event-feedback.md` | The coaching contract Claude follows. |
| `runner/systemd/personal-performance-feedback-dispatcher.{service,timer}` | Templates; not installed. |

Reused unchanged in behaviour: `workflow_runner.invoke_claude` (now takes an optional `json_schema`), `parse_claude_output`, `diagnose_claude_failure`, `redact_secrets`, `WorkflowLock`, `load_env_file`; `telegram_delivery.split_message`, plus a new `send_single_message` (one attempt, returns `message_id`) that the outbox uses instead of the Daily Review's internal retry. `event_store.py` now accepts schema v1 or v2 and never upgrades by itself.

## Data Flow (one run)

1. **Recover**: batches left `processing` longer than 45 min by a dead run — see Telegram Delivery for how each case is resolved without a duplicate.
2. **Intake** (one transaction): candidate events = `feedback_eligible=1`, `feedback_status='pending'`, `state IN (new, edited)`, no feedback item yet. Each is assessed (below): waiting events are left alone; excluded ones get a terminal item (`expired`/`suppressed` + reason) so they are never reconsidered; eligible ones are grouped and queued.
3. **Alerts**: an attention alert if the configured Claude login expiry date is within 7 days (date check only; no CLI call).
4. **Generate** (≤ 3 batches per run): gate (quiet hours, morning gate), Daily Review not running, auth preflight, daily budget → compare-and-set claim → **revalidate** every event → Claude call (≤ 1 corrective retry) → validate → message stored, batch moves to the deliver stage.
5. **Deliver**: claim → **revalidate** again → send parts in order, recording each `message_id` as it is sent → `delivered`, message text cleared.

### States

`feedback_items.state` and `feedback_batches.state`: `queued`, `processing`, `delivered`, `failed`, `expired`, `suppressed`. `feedback_batches.stage` (`generate` | `deliver`) says what a queued batch needs next.

Never twice: `feedback_items.event_id` is `UNIQUE` (one item, so one feedback, per event, ever); `feedback_batches.batch_key` is `UNIQUE` (`event:<ids>`, `digest:<date>`, `alert:<kind>:<date>`); claims are `UPDATE … WHERE state='queued'`; delivery is at-most-once (see Telegram Delivery).

## Eligibility and Event Timing

Four times are kept apart:

| Time | Source | Used for |
|---|---|---|
| Occurrence | activity end, else start | the historical cap, grouping, level |
| First seen | `events.first_seen_at` (late AthleteData sync shows here) | default eligibility time |
| Eligible since | the poller's `released` audit entry for a held Garmin strength activity, else first seen | settling, the notification window |
| Notification window | eligible since + 24 h | expiry of queued feedback |

Rules:

- **At intake only**: occurrence more than 48 h ago → `expired` / `stale_occurrence` (no unlimited historical feedback). Eligible for more than 24 h without being queued (e.g. dispatcher down) → `notification_window_passed`.
- **Before generation and before delivery**: the event must still be structurally eligible and inside its notification window. Occurrence age is *not* re-checked, so an accepted event never expires merely for waiting out quiet hours or the Daily Review (worst case ~11 h, well inside 24 h).
- A Garmin strength activity released after its 24 h hold starts its own window at release, so the hold never counts against it (tested end to end with the poller's own release logic). The same applies to late-arriving activities up to 48 h old.
- **Cutover**: events already eligible before the first live activation (`meta.feedback_activated_at`) that occurred more than 24 h before it → `pre_activation`. Events that become eligible after activation are judged normally.
- Events wait 10 min after becoming eligible (`SETTLE_DELAY`) so a related event from the next poll is grouped with them.

Other exclusions, with the reason recorded on the item: `baseline`, `backfill`, `deleted`, `superseded`, `not_eligible` (e.g. still held), `unverified_structure` (Apple Health while `APPLE_HEALTH_STRUCTURE_VERIFIED` is false — re-checked here even if a row says pending), `unknown_event_time`.

If an event becomes superseded/deleted after its message was generated but before any part was sent, the message is discarded and regenerated for the remaining events (or the batch is `suppressed`/`expired` if none remain). A generated message not delivered within 12 h is expired.

## Coaching Rules

Defined in `workflows/event-feedback.md`; the level is decided by the dispatcher from metadata only (it never sees workout contents):

- **SIGNIFICANT** if any of: a session of 90 min or more (`long_session`); Garmin and Hevy sessions in one group (`hybrid_day`); first training in 4+ days, only when the store's history covers those 4 days (`return_after_break`).
- **ROUTINE** otherwise. Body-composition events alone are always routine.

ROUTINE: brief assessment, alignment with `goals.md`, exactly one recommendation, ≤ 900 characters. SIGNIFICANT: detailed analysis with training-load / recent-performance / recovery context, 1–3 recommendations, ≤ 2,500 characters. Both use the existing priorities in `goals.md` (no new primary goal), `data-source-policy.md` source authority, and never read a single-day body-fat reading as a trend.

Validation rejects (and retries once, then backs off) output whose `workflow`, `batch_ref`, `level` or `events_covered` do not match, with the wrong number of recommendations, a SIGNIFICANT `completed` answer with no context, an over-long message, a code fence, any URL, or anything `redact_secrets()` would alter. A `safety_concern: true` answer gets an `[ATTENTION]` header.

## Quiet Hours

All decisions use Europe/Amsterdam wall time via `zoneinfo`, so they follow DST (tested on 2026-10-25 and 2027-03-28).

- 22:00–07:30: routine work is not generated or sent. Events detected then are attached to one `morning_digest` batch for the next morning (release 07:30 local); events detected before the digest is generated join it.
- 07:30–09:00: routine batches also wait until today's Daily Review has finished (`reviews/daily/<date>.md` exists and no `daily-review-*.lock`). From 09:00 they proceed regardless, so a failing Daily Review cannot block feedback.
- No Claude call starts while a Daily Review lock exists.
- Only `urgent` alerts bypass quiet hours. Today that is `claude_auth_escalation` alone; the expiry and budget alerts are `attention` and wait for the morning.

## Claude Authentication and Limits

- **Preflight**, run at most once per dispatch run and only when a generation is about to call Claude: CLI resolvable; `CLAUDE_AUTH_EXPIRES_ON` not passed; auth circuit closed; then `claude auth status --json`.
- `claude auth status` is non-generative: no prompt, no model request (≈0.7 s, local). Only its `loggedIn` boolean is read; the rest of its output (account e-mail, organisation) is discarded unread and never logged. No credential file is ever opened.
- **What it proves**: the CLI's locally stored login state (`assurance: local_cli_login_state` in the log). It is a local configuration check, *not* proof that the stored token will be accepted — an expired or revoked token can still read as logged in. Only a real call proves authentication, and every real call is classified.
- `loggedIn: false` → `cli_logged_out`, counted as an auth failure towards escalation. Unparseable output, timeout or a missing binary → `auth_status_unknown` (deferred, not counted, logged), so a future CLI output change stops feedback visibly rather than silently.
- **Classification** of real calls reuses `diagnose_claude_failure`: `claude_auth_failure`, `claude_quota_failure`, `claude_execution_failure`, plus `timeout`, `claude_not_found`, `malformed_output`.
- Auth failure and missing CLI are systemic: the batch is requeued **without** spending an attempt and no further Claude call is made that run. 3 consecutive auth failures → `urgent` alert (once per day) and a 6 h circuit breaker. Any answered call resets the counter.
- Other failures: up to 3 generation attempts per batch, backoff 15 min then 60 min, then `failed`.
- Daily budget `FEEDBACK_DAILY_CLAUDE_BUDGET` (default 6 invocations per local day, retries included, recorded in `claude_calls`). When exhausted, batches wait (and may expire) and one attention alert is queued.
- Set `CLAUDE_AUTH_EXPIRES_ON=2026-11-16` (the known refresh-token expiry) before go-live: an alert from 2026-11-09, and calls stop after the date instead of failing repeatedly.
- `--simulate` does not run `claude auth status` either (`assurance: none_simulation`).

## Telegram Delivery

Each part's `sendMessage` is preceded by a committed `inflight_part` marker and followed by a committed `parts_sent` + `message_id`. Outcomes:

| Outcome | Examples | Handling |
|---|---|---|
| Confirmed sent | HTTP 200 | recorded immediately; never sent again |
| Definitive, transient | 429 (honours `retry_after`, ≤ 1 h), 500/502/503, connect-phase network errors (DNS, refused, connect/TLS timeout — urllib raises these as `URLError` only before the request is fully sent) | retried: up to 4 delivery attempts, backoff 5/15/60 min |
| Definitive, permanent | other 4xx (bad token, chat not found, bot blocked) | `failed` / `telegram_rejected`; after fixing the cause an operator may run `--requeue-failed-delivery` (regenerates, since message text is not kept after failure) |
| Ambiguous | read timeout, connection reset after sending, 504, any unexpected error | `failed` / `delivery_outcome_unknown`; never retried, never requeued |

Crash recovery (lease 45 min): all parts confirmed → `delivered`; no send in flight → resumed from the first unconfirmed part; a send in flight → `delivery_outcome_unknown`. Generation crashes are simply requeued.

Once any part has been sent, the rest of that message is completed without revalidation or regeneration, so the athlete never receives two different versions. Telegram not configured → the batch stays queued and eventually expires.

**Unavoidable limitations**: Telegram's Bot API has no idempotency key, so delivery is at-most-once rather than exactly-once — an ambiguous outcome may mean the athlete received the message or did not, and the system will not guess. A 5xx other than 504 is assumed not delivered; if Telegram ever delivered and still returned such an error, a duplicate is possible. A message split into parts can be left partially delivered if a later part fails ambiguously.

## Database Migration (schema v2)

Additive only: new tables `feedback_batches` (batches and outbox: kind, urgency, level, state, stage, release/next-attempt times, generation and delivery attempt counts, last-attempt, generated and delivered timestamps, parts sent, the in-flight part marker, Telegram message IDs, message text until terminal + SHA-256 + length, error category), `feedback_items` (event → batch, state, level, reason), `claude_calls` (budget accounting), `dispatch_runs`; `meta.schema_version` → 2 and `meta.schema_v2_migrated_at`. No v1 table, column or row changes; fingerprints, cursors and baselines are untouched.

The migration runs in one `BEGIN IMMEDIATE` transaction, checks `integrity_check` and `foreign_key_check` before and after, is idempotent (a v2 store is verified and left alone), and refuses unknown versions or half-present v2 tables. `--migrate` first takes the poller's lock and writes an owner-only backup to `runtime/backups/events.v1.<UTC>.sqlite3`.

Compatibility (tested): every v1 row, fingerprint, Hevy cursor and baseline is byte-for-byte preserved; the real poller keeps polling, inserting and advancing its cursor on a migrated store, including while feedback rows reference its events; the Daily Review shares no table, lock or unit with either program, and its `invoke_claude` call is unchanged (the new schema parameter defaults to its own contract).

```bash
/usr/bin/python3 runner/feedback_dispatcher.py --migrate-check   # in-memory copy; reports v1_rows_preserved
/usr/bin/python3 runner/feedback_dispatcher.py --migrate         # production: only with approval
```

## Simulation Mode

```bash
cd /home/coach/personal-performance-system
/usr/bin/python3 runner/feedback_dispatcher.py --simulate
/usr/bin/python3 runner/feedback_dispatcher.py --simulate \
    --at 2026-10-22T21:30:00+02:00 --until 2026-10-23T09:30:00+02:00
```

Copies the store read-only into memory, migrates the copy, sets a simulated activation at `--at` if none exists, and runs the full pipeline every 15 minutes up to `--until` (max 7 days) with a gateway that never starts a process and a Telegram transport that only counts. It ignores `FEEDBACK_DISPATCH_ENABLED` and the real Telegram settings, creates no lock, backup or log file, and prints counts only: ineligible events by poller status, items by outcome and reason, batches by kind/level/state/release time, simulated Claude calls and messages. No identifiers, times of activities, message text or credentials are printed. Diagnostic JSON lines go to stderr.

`--status` prints the same aggregate counts for a migrated store (read-only).

## Deployment (requires approval; not done in Phase 4.3)

1. Deploy this code (the poller must run code that accepts v2 **before** the store is migrated; old poller code refuses a v2 store).
2. `/usr/bin/python3 -m unittest discover -s runner/tests`
3. `--migrate-check`, then `--migrate`; confirm `--status` and `event_poller.py --status` both report version 2 and the poller's next tick succeeds.
4. In `runner/config.env`: `CLAUDE_AUTH_EXPIRES_ON=2026-11-16`, `FEEDBACK_DAILY_CLAUDE_BUDGET=6`; leave `FEEDBACK_DISPATCH_ENABLED` unset.
5. Install the units (no `enable` yet), run `--simulate` again, then set `FEEDBACK_DISPATCH_ENABLED=true` and run one supervised `--once` during the day.
6. `sudo systemctl enable --now personal-performance-feedback-dispatcher.timer`

```bash
sudo cp runner/systemd/personal-performance-feedback-dispatcher.service /etc/systemd/system/
sudo cp runner/systemd/personal-performance-feedback-dispatcher.timer   /etc/systemd/system/
sudo systemctl daemon-reload
```

## Rollback

Stop feedback (either is enough):

```bash
# without root:
#   set FEEDBACK_DISPATCH_ENABLED=false in runner/config.env
sudo systemctl disable --now personal-performance-feedback-dispatcher.timer
sudo rm /etc/systemd/system/personal-performance-feedback-dispatcher.{service,timer}
sudo systemctl daemon-reload
```

The v2 tables are inert without the dispatcher and the poller works on v2, so the store can stay migrated. To return the schema to v1, prefer the lossless downgrade:

```bash
/usr/bin/python3 runner/feedback_dispatcher.py --downgrade-v1
```

It takes both locks, writes `runtime/backups/events.v2.<UTC>.sqlite3`, then drops only the four v2 tables and resets `schema_version` to 1 in one transaction — every detection made since the migration is kept. Only after that may code older than Phase 4.3 be redeployed (`git revert`), because old poller code refuses a v2 store.

Restoring the v1 backup instead (`runtime/backups/events.v1.*.sqlite3`, with the poller timer stopped) also works but discards everything detected since the migration; those events are then re-detected as new, or as backfill if older than 3 days.

Backup considerations: backups are owner-only (`0600`) copies under the gitignored `runtime/backups/` and contain the same identifiers and HMAC fingerprints as the live store (no workout contents or measurements), so they need the same protection; they remain valid only with the unchanged `runtime/event-poller.key`. They are not rotated automatically — delete them once the migration has proven itself. The Daily Review and poller units are never touched by any of these steps.
